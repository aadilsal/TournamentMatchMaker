### [Critical] C-1 Knockout bracket cannot advance — every knockout match completion 500s

**Where:** `apps/api/src/modules/tournaments/tournaments.service.ts:1222`, via `apps/api/src/lib/match-outcome.ts:159`
**Steps to reproduce:**
1. Tournament in `phase='knockout'`, a `confirmed` match at `round_number=102`, `bracket_slot=0`.
2. Submit both players' scores via the Meta API.
**Expected:** winner advances; a Final row is created with the winner in one side.
**Actual:** HTTP **500**. Server exception:
```
null value in column "player2_id" of relation "matches" violates not-null constraint
  at TournamentsService.advanceKnockoutWinner (tournaments.service.ts:1222)
  at applyMatchOutcome (match-outcome.ts:159)
```
`advanceKnockoutWinner` inserts the next-round match with the undecided side as `NULL`, but `matches.player1_id` and `matches.player2_id` are both `NOT NULL` (verified in `information_schema`).
**Suspected cause:** the INSERT at `tournaments.service.ts:1222-1232` is incompatible with the table constraint. Either make the player columns nullable for pending bracket slots, or defer creating the next-round row until both feeder matches resolve.
**Severity note:** the match result *is* committed before this throws, so the score lands, ratings apply, and then the caller gets a 500 — the headset will retry and get `409 Player 1 score already submitted`. The bracket never progresses. This makes P4 #8's "two Final rows" impossible to hit because **zero** Final rows can ever be created.

### [Critical] C-3 Meta integration auth fully bypassed when `META_SSH_PUBLIC_KEY` is unset

**Where:** `apps/api/src/middleware/metaAuth.ts:11`, `apps/api/src/config/env.ts:21`
**Steps to reproduce:** run the API with `META_SSH_PUBLIC_KEY` absent (the zod schema declares it `.optional()`, so the app boots happily), then call any Meta endpoint **with no headers at all**.
**Expected:** 401.
**Actual (reproduced against the real middleware + real env type):**
```
200  no headers at all      -> {"reached":"PROTECTED HANDLER"}
200  wrong api key          -> {"reached":"PROTECTED HANDLER"}
500  wrong ssh key          -> blocked
200  correct api key        -> {"reached":"PROTECTED HANDLER"}
```
`sshPublicKey === env.META_SSH_PUBLIC_KEY` becomes `undefined === undefined` → `true`. Sending a *wrong* key is correctly blocked; sending **nothing** passes. Every Meta endpoint (submit score for any match, read any player's current match, solo target, link-code verify) is open.
**Current environment is NOT vulnerable** — `META_SSH_PUBLIC_KEY` is set in `.env`, and I confirmed live 401s on all four endpoints with no headers. This is one missing env var away in any other deployment.
**Fix:** reject empty/undefined configured keys before comparing, and make the var required (or drop the SSH path).

### [Critical] C-4 Buyback fulfilled into a tournament phase that has already moved on

**Where:** `apps/api/src/modules/tournaments/tournaments.service.ts:789` (`fulfillBuyback`)
**Steps to reproduce:** create a pending buyback for an eliminated participant, advance the tournament, then deliver `payment_intent.succeeded` for that buyback.
**Expected:** reject or refund, or reconcile the player into the current phase.
**Actual — all three variants set the participant back to `active` and charge them:**

| State when the webhook lands | participant after |
|---|---|
| round 1 `closed`, `ends_at` in the past | `eliminated` → **`active`**, `buyback_count` 0 → 1 |
| tournament advanced to `phase='knockout'` | `eliminated` → **`active`** |
| tournament `status='completed'`, `phase='completed'` | `eliminated` → **`active`** |

**Suspected cause:** `createBuybackCheckout` (`:753`) validates phase, participant status, knockout threshold and round `ends_at > NOW()` — but `fulfillBuyback` re-validates **none** of it. It reads the buyback row and immediately flips the participant to `active` and requeues into the stale `buyback.round_number`.
**Observed side effect:** the player ends up `active` but *not* in the tournament queue — a limbo state where they appear alive in the standings but cannot be paired.

### [Critical] C-5 Buyback double-grant under concurrent webhook delivery

**Where:** `apps/api/src/modules/tournaments/tournaments.service.ts:795-824`
**Steps to reproduce:** one pending buyback; fire two identical signed `payment_intent.succeeded` events with `Promise.all`.
**Expected:** `buyback_count` +1, one requeue, one notification.
**Actual:**
```
before:              participant=eliminated buyback_count=0 buyback=pending
webhook responses:   [200, 200]
after 2x concurrent: participant=active     buyback_count=2 buyback=completed
```
Sequential replay of the same event is correctly idempotent (`buyback_count` stays 1) — the defect is specifically the race.
**Suspected cause:** classic check-then-act. The `status === 'completed'` guard at `:795` is an unlocked read *outside* the transaction; the transaction then runs an unconditional `UPDATE buybacks SET status='completed'` (`:814`, no `WHERE status='pending'`) and `buyback_count = buyback_count + 1` (`:821`). Both webhooks pass the guard and both increment.
**Realistic trigger:** Stripe retries webhooks and can deliver duplicates concurrently.
**Fix:** `SELECT … FOR UPDATE` the buyback row inside the transaction, and make the status update conditional (`WHERE id=$1 AND status='pending'`); treat 0 rows affected as already-fulfilled.

## Part 4 / Part 3 — High

### [High] H-1 Buyback checkout retry after a successful payment loses the customer's money

**Where:** `apps/api/src/lib/stripe.ts:67-85` and `:137-140`
**Steps to reproduce (code-confirmed trigger; consequence tested live):** pay a buyback successfully, then re-click checkout before Stripe's webhook lands.
**What the code does:** `createBuybackPaymentIntent` retrieves the existing intent. A succeeded intent is not in the allowed set (`requires_payment_method` / `requires_confirmation` / `requires_action`), so it falls through to
`UPDATE buybacks SET status='failed' WHERE id=$1 AND status='pending'` (`:82`) and creates a **new** PaymentIntent — a second charge.
**Consequence, verified live:** once a buyback is `failed`, the genuine `payment_intent.succeeded` for the original payment is silently swallowed:
```
before: buyback=failed, participant=eliminated, buyback_count=0
succeeded webhook -> 200 {"received":true}
after:  buyback=failed, participant=eliminated, buyback_count=0
```
`fulfillBuybackFromWebhook` (`stripe.ts:137`) logs a warning and returns. Player paid; got nothing; webhook reports success to Stripe.
**Not tested:** the live double-charge itself — see C-0.
**Fix:** treat `intent.status === 'succeeded'` as "already paid, go fulfil", never as a failure.

### [High] H-3 Demoted admins keep admin access, and "revoke sessions" does not revoke

**Where:** `apps/api/src/middleware/auth.ts` / `admin.ts` (role read from JWT claim)
**Steps to reproduce:**
1. Promote a player to `venue_admin`; log in as them → `GET /admin/dashboard` = 200.
2. Demote them back to `player`. DB role is now `player`.
3. Reuse the same access token → `GET /admin/dashboard` = **200**.
4. Call `DELETE /admin/users/:id/sessions` (returns 200), retry → still **200**.

**Expected:** demotion takes effect immediately, or at minimum the documented remedy (revoke sessions) works.
**Actual:** admin authorization is decided purely by the `role` claim in the JWT, so a demoted or compromised admin retains full powers until natural expiry (~15 min), and the emergency revoke control is a no-op for access tokens.
**Note:** `POST /auth/logout` *does* invalidate the access token (verified), so a revocation mechanism exists — the admin path just doesn't use it. That makes this cheap to fix.

### [High] H-4 A confirmed match with no time slot never expires — permanent requeue lockout

**Where:** `apps/worker/src/jobs/expire-unplayed-slots.job.ts:16-22`, `apps/worker/src/jobs/expire-matches.job.ts:16-20`
**Steps to reproduce:**
```
A) clean state, join global queue          -> 201
B) create confirmed slotless match (5h old)
   join global queue                       -> 409 {"CONFLICT","You have an active match"}
C) after admin "Expire stale matches" + 70s of worker cycles: status = confirmed
```
| Match | Result after admin expire + 70s |
|---|---|
| casual, no slot, `pending_confirmation`, 3h old | EXPIRED — correct |
| casual, no slot, **`confirmed`**, 3h old | **STILL CONFIRMED** |
| casual, no slot, **`in_progress`**, 3h old | **STILL IN_PROGRESS** |

**Suspected cause:** `expire-unplayed-slots.job.ts` uses `JOIN time_slots ts ON ts.id = m.time_slot_id` — an inner join, so `time_slot_id IS NULL` rows are never selected. `expire-matches.job.ts` only considers `status='pending_confirmation'`. Nothing covers a confirmed slotless match, including the admin bulk action (it reported `{"expired":6}` while leaving both).
**Reachable path:** two VR players pairing in the **global** (non-tournament) queue get `chosenSlot = null`, and once both confirm, the match becomes immortal — both players are blocked from ever requeuing.

### [High] H-5 Admin "Broadcast to all players" always fails with a 500

**Where:** `POST /admin/notifications/broadcast`, `apps/api/src/modules/admin/services/buybacks-notifications.service.ts:257`
**Steps to reproduce:** as **superadmin**, POST any schema-valid body (`{type:'system'}`, with/without channel/payload — all tried).
**Actual:** `500 {"code":"INTERNAL_ERROR"}` every time; zero notifications sent.
**Root cause (reproduced directly):**
```
THREW: Error | Custom Id cannot contain :
  at Job.validateOptions (bullmq/dist/cjs/classes/job.js:1049)
```
BullMQ 5.78 rejects a custom `jobId` that contains `:` unless it splits into **exactly 3** parts. The broadcast key is `broadcast:${Date.now()}:${userId}:${input.type}` → 4 parts → throws on the first recipient.
**Fix:** use a delimiter other than `:` (or exactly 3 segments).

### [High] H-6 Buyback completion notification is silently never sent

**Where:** `apps/api/src/modules/tournaments/tournaments.service.ts:846`
Same BullMQ rule as H-5: `buyback:${buybackId}` is **2** parts → throws. The call is wrapped in `.catch(console.error)`, so it fails silently — a player who successfully buys back is never told. Confirmed across every buyback test in this run (`notifs=0`).

| Key shape | Parts | Result |

| `tournament-reg:<t>:<u>`, `match-cancelled-withdrawal:<m>:<u>`, `admin-test:<u>:<ts>` | 3 | OK |
| **`buyback:<id>`** | **2** | **THROWS** |
| **`broadcast:<ts>:<u>:<type>`** | **4** | **THROWS** |

### [High] H-7 `pnpm db:reset` and `pnpm seed` have no database guard whatsoever

**Where:** `packages/db/scripts/db-reset.mjs`, `packages/db/seeds/dev.ts`
`db-reset.mjs` loads `.env` with `override: true` and unconditionally runs `DROP TABLE IF EXISTS … CASCADE` on `bookings`, `time_slots`, `venues`, `refresh_tokens`, `users`, `pgmigrations`. There is **no** check on `DATABASE_URL`, no `NODE_ENV` check, no host allowlist, no confirmation prompt. `seeds/dev.ts` likewise deletes matches, buybacks, notifications and time slots with no guard.
**Why this matters here specifically:** this repo's `.env` already contains **live** Stripe credentials (C-0), which is direct evidence that production secrets get pasted into this file. If a production `DATABASE_URL` ever lands there, `pnpm db:reset` drops the users table.
**Not executed** — the finding is conclusive from the source, and running it would have destroyed the test environment mid-run.
**Secondary:** the drop list is stale relative to the current schema (it omits `tournaments`, `matches`, `buybacks`, `tournament_*`), so even in dev it leaves a half-reset database.

### [High] H-8 Queue join accepts slots the pairer will always reject — players queue forever

**Where:** `apps/api/src/modules/matchmaking/matchmaking.service.ts:118-131` vs `apps/worker/src/jobs/pair-players.job.ts:146-152, 182-203`
**Steps to reproduce:** 20 registered VR players, all with a `tournament_round_slots` row for a slot that is in the future but starts ~3 minutes *before* the active round's `starts_at`; all join the tournament queue.
**Actual:** all 20 joins return **201**, the queue fills, the worker runs pairing jobs continuously, and **0 matches** are created. Re-running with a slot inside the round window → 20/20 paired into 10 matches immediately.
**Cause:** join validates the slot only with `ts.end_time > NOW()`. The pairer additionally requires `slot.startTime >= round.startsAt && slot.endTime <= round.endsAt` (`slotWithinRound`); when that fails, `chosenSlot` is null and, for a tournament match, it rolls back and emits `queue:pair_failed` — leaving the player in the queue.
**Player-visible symptom:** "Finding opponent…" forever, with no explanation, and the entry was accepted so nothing looks wrong. Also explains the `qa-brutal.mjs` baseline failure "VR pairing — >12s or queue not cleared".
**Fix:** apply the same round-window check at join time and reject with a specific message.

### [High] H-9 Rate limiting fails open if Redis is unavailable

**Where:** `apps/api/src/middleware/rateLimit.ts:49-51`
`createRateLimiter` wraps everything in `try { … } catch { next(); }`. If Redis is down or the key errors, every limiter silently disappears — including `credentialRateLimit`, the credential-stuffing defence. A Redis blip converts the login endpoint into an unlimited brute-force target with no signal.
**Note:** the limiters themselves are well-designed and work correctly (verified: 25 concurrent bad logins → all 429; per-IP 50/5min and per-account 10/15min; email padding does not create a fresh bucket — ` user@x` is rejected as a 400 before it reaches the limiter). This is purely the failure mode.

## Medium / Low

### [Medium] M-1 The same email can register twice in different cases
`Case…@Test.com` and `case…@test.com` both registered successfully (201, 201) → 2 rows. Logging in with the lowercase form resolves to one of them (200). Creates duplicate identities and ambiguity for password reset and support.
Note the credential limiter *does* lowercase its bucket key (`rateLimit.ts:151`), so registration and rate limiting disagree about identity.
**Fix:** unique index on `lower(email)` plus normalise on write.

### [Medium] M-2 `users.role` has no CHECK constraint
`role` is a plain `varchar` with no constraint (the only CHECK on the table is `skill_tier BETWEEN 1 AND 5`). The API validates, but any direct write or future code path can store an arbitrary role string. Given C-2/H-3 read authorization straight from this column into the JWT, it's worth constraining.

### [Low] L-1 The seeded buyback demo scenario cannot be exercised
`pnpm seed` advertises *"Buyback → login imam_lefty / password123 → /matches"*, but seeds `imam_lefty` as `eliminated` in **Lahore VR Championship**, which is seeded in `phase='knockout'`. `createBuybackCheckout` correctly rejects with *"Buybacks are only available during normal rounds"*, so `GET /players/me/buyback-options` returns `[]` and the buyback UI never appears. Both `qa-brutal.mjs` and `qa-brutal-extended.mjs` report this as a failure/warning.
**Fix:** seed the eliminated player into a `normal`-phase tournament with an active round.

### [Low] L-2 Confirm dialog uses `role="alertdialog"`, not `role="dialog"`
`ADMIN_UX_FIXES.md` section 1 claims `role="dialog"`. The shipped component uses `role="alertdialog"` with `aria-modal="true"`, `aria-labelledby`, `aria-describedby`. This is arguably **more** correct for a destructive confirmation — flagged only so the doc matches reality, and because automated checks keyed on `[role="dialog"]` will miss it (mine did).
