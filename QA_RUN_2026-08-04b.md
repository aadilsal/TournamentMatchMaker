## The bugs found

### [Medium] A venue admin could read every player's notifications through the API

**Where:** `apps/api/src/modules/admin/admin.routes.ts` — the `/notifications`, `/matches` and `/buybacks` **list** endpoints
**Found:** while fact-checking the permissions table for `HANDOVER.md` — the admin sidebar hides these sections from a `venue_admin`, so it was worth confirming the server agreed.
**Steps to reproduce:** as a `venue_admin`, `GET /api/v1/admin/notifications`.
**Expected:** 403 — the section is not part of that role.
**Actual:** **200 with 100 rows** (page limit) out of 168 in the system, including other players' personal notification payloads. `/matches` returned all 48; `/buybacks` was likewise open.

**Cause:** Suite E covers out-of-scope *mutations* and *specific-resource reads*, which were all correctly blocked. These three **list** endpoints had no role guard at all — only the browser sidebar hid them, and hiding in the UI is not access control.

**Fix:** the three lists now carry `requireAdminRoles('tournament_admin')`, which mirrors the sidebar's own role map and always admits superadmin.

**Verified:**

```
section                venue_admin  tournament_admin  superadmin
GET /notifications     403          200               200
GET /matches           403          200               200
GET /buybacks          403          200               200
GET /venues            200          200               200
GET /bookings          200          200               200
```

Venue and booking lists were already correctly filtered (1 of 7 venues; 0 bookings at other venues). Tournament lists stay open to all admins because tournaments are public data — the unauthenticated endpoint already returns them.

### [High] Tournament capacity was not enforced under concurrency

**Where:** `apps/api/src/modules/tournaments/tournaments.service.ts` — `register()`
**Steps to reproduce:** create a tournament with `maxPlayers: 3`; fire 8 registrations with `Promise.all`.
**Expected:** 3 accepted, 5 refused with "Tournament is full".
**Actual:** **all 8 accepted** — `HTTP 201,201,201,201,201,201,201,201`, 8 rows in `tournament_registrations`.

**Cause:** the capacity check read `registrationCount` from a `getById()` outside the transaction. Every request in a simultaneous burst saw the same pre-insert count, all passed the check, and all inserted. Sequentially it was enforced correctly (Suite B3 passes), so it only appeared under real concurrency — the same shape as the buyback double-grant race fixed earlier.

**Fix:** take `SELECT … FOR UPDATE` on the tournament row inside the transaction and re-count under that lock before inserting. The cheap pre-check is kept so an obviously-full tournament still fails fast. The re-count excludes the registering user (`user_id <> $2`) so re-registering stays idempotent rather than being rejected by the place they already hold.

**Verified:** `3 registered, HTTP 201,201,201,409,409,409,409,409` — and Suites B and C re-run clean afterwards, so normal registration is unaffected.

## What each suite established

**A — lifecycle.** Registration closing *exactly now* is picked up; closing in 1 minute is not closed early. A tournament with every stage already due walks `open → closed → in_progress → completed` in one sweep rather than stalling midway. A settled tournament is never touched again (`updated_at` unchanged across a later sweep). Null registration windows and tournaments with no rounds neither crash the sweep nor get closed by mistake, and a canary confirms the sweep is still healthy afterwards. An admin completing a tournament in the same moment the sweep wants to start it is **not** reverted. The API rejects end-before-start, close-before-open and close-after-start; a direct DB insert with an inverted window is refused by the CHECK constraint.

**B — registration window.** Closed one second ago → refused; opens tomorrow → refused; inside the window → accepted. Legacy rows with a NULL window still register. Capacity refused correctly in the sequential case. Two simultaneous registrations create exactly one row. Every non-`open` status is refused even with an open window. Admin can edit the close time, and an inverted edit is rejected. The window is present on the public payload.

**C — live participation.** `active`/`advanced`/`knockout`/`eliminated` all block joining elsewhere and the banner names the tournament; `out` allows it. Withdrawing sets the participant to `out`, clears `liveTournament` and frees the player immediately. An eliminated player with a live buyback stays locked *and* still sees their buyback option. Completing the tournament releases everyone. A race across two tournaments cannot produce two live rows, and the DB index refuses one directly.

**D — session / socket.** No token, garbage token and empty-string token are all refused. Player A's events reach only A — **zero** leaked to B. Logout disconnects the socket, emits `session:revoked`, 401s the REST token and blocks reconnection. Suspension and demotion both drop live sockets. Emitting `match:confirmed` for a match you're not in returns an error rather than silently applying.

**E — admin scope.** 40 out-of-scope actions × `venue_admin` and `tournament_admin` — **all 403**, including the escalation paths (adding admins to venues/tournaments) and every lifecycle action. In-scope work still succeeds, and superadmin remains unrestricted.

**F — regression.** Knockout advancement returns 200 and produces exactly one Final with both winners. Two concurrent buyback webhooks grant exactly one; a buyback is refused when the round has closed, knockout has started, or the tournament has completed; a `failed` buyback is not fulfilled by a later success. Meta endpoints 401 without headers. Ten concurrent scores apply exactly one win and one loss, and every malformed score value is rejected. Slotless `confirmed`/`in_progress` matches expire. Broadcast delivers rows. Case-variant duplicate emails refused; malformed bodies 4xx.

**G — concurrency.** 12 simultaneous entries → 6 matches, nobody double-paired or stranded. One capacity-1 slot from 6 sessions → exactly 1 booking, clean 409s. Three simultaneous `close-registration` calls leave a consistent status with no 500s. 60 concurrent reads in 210 ms.

**H — browser.** All player and admin pages render. Banner + disabled "Already playing" appear and clear correctly. A round starting now and running 2 days offers exactly 3 days (`Today 4 Aug, Wed 5 Aug, Thu 6 Aug`). The admin form marks 9 required fields and surfaces validation. No horizontal overflow at 375 px. No unexpected console or page errors across the whole run.

## Two test-harness faults corrected (not product bugs)

Worth recording so the next run doesn't re-raise them:

- **Suite C initially reported withdraw broken (404).** The endpoint is `DELETE /tournaments/:id/register`, not `POST …/withdraw`. Corrected; withdraw works.
- **Suite E initially reported a `venue_admin` booking bypass.** `select id from bookings limit 1` without `ORDER BY` is non-deterministic and returned a booking at the admin's *own* venue, where 200 is correct. A dedicated test (E2) against a booking definitely at another venue confirms READ/EDIT/CANCEL are all 403, and an own-venue booking is still readable. Suite E's fixture now picks deterministically.
